> **상태:** 구현 반영 (MVP)  
> **작성 기준:** 2026-07-24  
> **정렬 기준 코드:** `backend/app/services/transfer.py`, `web/mypage.html`, `HKUI.reservationCard`, `enqueue_teams_message` / `deliver_teams_messages`

같은 주(사이클) **확정 예약끼리 슬롯을 맞바꾸는** 기능입니다.  
양도와 달리 **상대(피제안자) 수락**이 필요하고, **관리자 승인은 없습니다**(현재 양도와 동일하게 peer-only).

## 1. 비즈니스 규칙 (확정)

1. **대상:** 같은 `cycle_id`(이용 주차)의 **CONFIRMED** 예약끼리만 교환 가능.  
   - 제안자·피제안자 모두 본인 예약이 `CONFIRMED` 여야 함.  
   - 허용 예약 유형(MVP): `NORMAL`, `REAPPLY`, `TRANSFER`, **`ADMIN_ASSIGN`**  
     (확정 슬롯이면 제안자·피제안자 **양쪽 모두** 후보/대상 가능. 나머지 규칙과 동일 적용.)
2. **가능 시간창:** 양도와 동일하게  
   `cycle.close_at`(수 17:00) ≤ now &lt; **본인 슬롯 시작**.  
   추가 조건: **제안 시점·수락 시점 모두**에서  
   - 제안자: `now < proposer_slot.start`  
   - 피제안자: `now < target_slot.start`  
   (둘 중 하나라도 슬롯이 시작됐으면 제안/수락 불가.)
3. **대기 한도:** 예약당 **PENDING 교환제안 최대 1건**.  
   - 제안자 예약·피제안자 예약 각각에 대해 PENDING이 있으면 신규 제안/양도 불가.  
   - **양도(`transfer`)와 교환제안은 동시에 진행 불가** (어느 쪽이든 PENDING/진행 중이면 상대 액션 차단).  
   - ※ 현재 양도는 즉시 완료라 PENDING이 거의 없으나, 레거시 PENDING·동시 요청 레이스를 위해 동일 배제 규칙을 둡니다.
4. **제안자 취소:** PENDING인 동안 제안자가 취소 가능 → 상태 `CANCELLED` → **피제안자에게 Teams 알림** (`SWAP_CANCELLED`, 확정).  
5. **피제안자 거절:** PENDING → `REJECTED` → **제안자에게 Teams 알림** (`SWAP_REJECTED`, 확정).  
6. **수락 직전 재검증:** Accept 시 FOR UPDATE 후 즉시 재검사. 실패 시 제안은 실패 종료(`FAILED` 또는 `REJECTED`+사유 — 아래 스키마)하고 **실패 Teams는 제안자에게** 발송.  
   실패 예시(필수):  
   - 이미 양도됨 / 예약이 더 이상 CONFIRMED 아님  
   - 예약 취소됨  
   - 시간창 지남(수 17:00 이전으로 되돌아갈 일은 없고, **어느 한쪽 슬롯 시작 시각 경과**)  
   - 상대가 다른 PENDING 교환/양도와 충돌  
7. **관리자 승인 없음.** FO peer만으로 완료. BO 메뉴/배지 없음(MVP).
8. **완료 시 처리 원칙:** 두 예약의 `slot_id`를 **맞교환**하고, 각 `slot.confirmed_reservation_id`를 갱신.  
   - 새 `Reservation` 행을 만들지 않음(양도의 CANCELLED+신규 TRANSFER와 다름).  
   - `type` / `confirmed_by`는 유지(원본 이력 보존).  
   - `last_used_date`는 양도와 같이 양측 `recompute_member_last_used_date` 호출.

## 2. UX · 화면 카피

### 2.1 버튼 배치 (마이페이지 예약 카드)

기존 `HKUI.reservationCard` 액션 영역과 정렬.

| 상태 | 액션 UI |
| --- | --- |
| 교환 가능 (`swappable`) | 보조 버튼 **교환하기** (+ 기존 **양도하기**와 나란히 또는 overflow) |
| 내가 보낸 PENDING | 배지 **교환 제안 중** + 상대 이름 · 버튼 **제안 취소** |
| 내가 받은 PENDING | 카드/인박스에서 **수락** / **거절** |
| 양도 진행 중 / 교환 PENDING(상대 예약 포함) | 교환·양도 버튼 비활성 또는 숨김 |
| 창 미오픈 (`swapOpensAt`) | disabled **교환하기** + 툴팁「수 17:00 이후 교환할 수 있어요」 |
| 슬롯 지남 (`swapEnded`) | disabled +「예약 시간이 지나 교환할 수 없습니다」 |

**권장 레이아웃 (확정 카드):**

- 1행: 날짜·시간 · 상태 배지  
- 액션: `[교환하기]` `[양도하기]` (둘 다 secondary sm)  
- 모바일: 버튼 2개가 좁으면 **교환하기**를 우선 노출하고 양도는 동일 행 wrap.

> 안내 문구(페이지 상단 alert 보강):  
> 「확정 후 **수 17:00 이후** 다른 확정 회원과 **슬롯 교환**을 제안하거나, 예약이 필요 없으면 **양도**할 수 있습니다.」

### 2.2 교환하기 모달 (제안자)

양도 모달과 유사하되, **검색어 입력 전에는 후보 목록을 보여 주지 않음** (검색 결과만 표시).

| 요소 | 카피 |
| --- | --- |
| 제목 | 교환하기 |
| 안내 | 같은 주 **확정 예약** 회원을 검색해 슬롯 교환을 제안합니다. 상대가 **수락**하면 서로 시간이 바뀌고, **거절·실패 시** Teams로 알려 드립니다. 관리자 승인 없음. |
| 검색 placeholder | 이름, 이메일, 부서로 검색 |
| 초기(미검색) | 이름을 검색하세요 |
| 목록 항목 | `{이름}` · `{부서}` · **{요일} {시작}–{종료}** |
| 검색 후 빈 목록 | 검색 결과가 없습니다. |
| 확인 다이얼로그 | **교환할까요?** / `<b>{이름}</b>님의 <b>{상대슬롯}</b>과 내 예약 <b>{내슬롯}</b>을 맞바꾸자고 제안합니다. 상대 수락 전까지 양도·다른 교환은 할 수 없습니다. |
| 제출 버튼 | 교환하기 → 진행 중 **교환 중…** |
| 성공 토스트 | 교환 제안을 보냈습니다 |
| 에러 토스트 | API `message` 그대로 (아래 에러 코드) |

### 2.3 받은 제안 인박스 (FO · 신규)

**위치:** 마이페이지 예약 내역 **위**에 「받은 교환 제안」 섹션 (PENDING만).

| 상태 | UI |
| --- | --- |
| 수신 0건 | 섹션 숨김 (또는 접힌 빈 상태 미노출) |
| 수신 N건 | 카드 리스트 + 배지 숫자 |

**카드 카피 예시:**

- 제목: **{제안자이름}님의 교환 제안**
- 본문: 내 예약 `{내날짜} {내시간}` ↔ 상대 `{상대날짜} {상대시간}`
- 버튼: **수락** / **거절**
- 확인(수락): **교환을 수락할까요?** / 수락 즉시 슬롯이 바뀌며 Teams로 안내됩니다.
- 확인(거절): **제안을 거절할까요?** / 제안자에게 Teams로 거절이 전달됩니다.
- 성공 토스트: 교환이 완료되었습니다 / 제안을 거절했습니다
- 수락 실패 토스트: 교환할 수 없는 상태입니다. 제안자에게 안내를 보냈습니다.

### 2.4 보낸 제안 / 상태 라벨

| 상태 | 라벨 | 비고 |
| --- | --- | --- |
| PENDING (보낸) | 교환 제안 중 → {상대이름} | **제안 취소** |
| PENDING (받은) | 교환 제안 받음 ← {제안자} | 인박스 |
| ACCEPTED | (예약 카드 시간만 갱신) | 별도 배지 불필요 |
| REJECTED | 토스트/Teams만 | 카드에서 PENDING 해제 |
| CANCELLED | 제안이 취소되었습니다 | 토스트 |
| FAILED | 교환에 실패했습니다 | Teams(제안자) + 토스트(수락 시도자) |

### 2.5 에러 토스트 (대표)

| code | 사용자 메시지 (권장) |
| --- | --- |
| `NOT_SWAP_PERIOD` | 교환 가능 시간(수요일 17:00 이후 ~ 예약 시작 전)이 아닙니다. |
| `NOT_SWAPPABLE` | 교환할 수 없는 예약입니다. |
| `TARGET_NOT_SWAPPABLE` | 선택한 회원과 교환할 수 없습니다. (확정·같은 주·시간 조건) |
| `SWAP_ALREADY_PENDING` | 이미 진행 중인 교환 제안이 있습니다. |
| `TRANSFER_IN_PROGRESS` | 양도 진행 중이라 교환할 수 없습니다. |
| `SWAP_IN_PROGRESS` | 교환 제안 진행 중이라 양도할 수 없습니다. |
| `SLOT_ALREADY_STARTED` | 예약 시간이 지나 교환할 수 없습니다. |
| `SWAP_NOT_PENDING` | 이미 처리된 제안입니다. |
| `FORBIDDEN` | 권한이 없습니다. |

## 3. Teams 메시지 템플릿

발송 패턴: `enqueue_teams_message` → API 응답 후 `background_tasks.add_task(deliver_teams_messages, ids)` (양도와 동일).

`TeamsMessageType` 추가 제안:

| enum | 용도 |
| --- | --- |
| `SWAP_PROPOSED` | 피제안자에게 제안 도착 |
| `SWAP_REJECTED` | 제안자에게 거절 통지 (**확정**) |
| `SWAP_ACCEPTED` | 양측에게 완료 통지 |
| `SWAP_ACCEPT_FAILED` | 제안자에게 수락 실패 통지 |
| `SWAP_CANCELLED` | 피제안자에게 취소 통지 (**확정**) |

> **거절 ≠ 취소 (Teams 수신자 혼동 주의)**  
> - **거절:** 피제안자가 거절 → Teams는 **제안자**에게 “거절됨” (`SWAP_REJECTED`, 확정).  
> - **취소:** 제안자가 PENDING 제안을 직접 철회 → Teams는 **피제안자**에게 “제안이 취소됐어요” (`SWAP_CANCELLED`, 확정).

### 3.1 제안 (`SWAP_PROPOSED`) → 피제안자

```html
<p><strong>[헬스키퍼]</strong> 예약 교환 제안</p>
<p>{targetName}님, <b>{proposerName}</b>님이 슬롯 교환을 제안했습니다.</p>
<p>내 예약: <strong>{targetSlot}</strong></p>
<p>상대 예약: <strong>{proposerSlot}</strong></p>
<p>마이페이지에서 수락 또는 거절해 주세요.</p>
```

### 3.2 거절 (`SWAP_REJECTED`) → 제안자

```html
<p><strong>[헬스키퍼]</strong> 교환 제안 거절</p>
<p>{proposerName}님, <b>{targetName}</b>님이 교환 제안을 거절했습니다.</p>
<p>내 예약: <strong>{proposerSlot}</strong> / 상대: <strong>{targetSlot}</strong></p>
<p>예약은 그대로 유지됩니다.</p>
```

### 3.3 수락 성공 (`SWAP_ACCEPTED`) → 양측

제안자용:

```html
<p><strong>[헬스키퍼]</strong> 예약 교환 완료</p>
<p>{proposerName}님, <b>{targetName}</b>님과 예약 교환이 완료되었습니다.</p>
<p>변경 후 예약: <strong>{newProposerSlot}</strong></p>
```

피제안자용: 대칭 카피 (`변경 후 예약: {newTargetSlot}`).

### 3.4 수락 실패 (`SWAP_ACCEPT_FAILED`) → 제안자 (필수)

```html
<p><strong>[헬스키퍼]</strong> 교환 진행 실패</p>
<p>{proposerName}님, <b>{targetName}</b>님과의 교환을 진행할 수 없어 제안이 종료되었습니다.</p>
<p>사유: {failReasonKo}</p>
<p>내 예약: <strong>{proposerSlot}</strong> (변동 없음)</p>
```

`failReasonKo` 예시:

- 상대 예약이 이미 양도·취소되었습니다.
- 예약 시작 시간이 지나 교환할 수 없습니다.
- 예약 상태가 변경되어 교환할 수 없습니다.

### 3.5 취소 (`SWAP_CANCELLED`) → 피제안자 (**확정**)

제안자가 PENDING 제안을 **직접 철회**했을 때 피제안자에게 발송.  
※ 거절(`SWAP_REJECTED` → 제안자)과 수신자·카피가 다름.

```html
<p><strong>[헬스키퍼]</strong> 교환 제안 취소</p>
<p>{targetName}님, <b>{proposerName}</b>님의 교환 제안이 취소됐어요.</p>
<p>내 예약: <strong>{targetSlot}</strong> (변동 없음)</p>
```

## 4. DB 스키마 — `swap_proposal`

`transfer_request`를 재사용하지 않음. 양도(일방 이전·즉시 완료)와 의미가 다름.

### 4.1 Enum

```text
SwapProposalStatus:
  PENDING
  ACCEPTED
  REJECTED
  CANCELLED   # 제안자 취소
  FAILED      # 수락 시 재검증 실패 (슬롯 변경 없음)
```

### 4.2 테이블

```sql
CREATE TABLE swap_proposal (
  id                        BIGSERIAL PRIMARY KEY,
  cycle_id                  BIGINT NOT NULL REFERENCES reservation_cycle(id) ON DELETE CASCADE,

  proposer_member_id        BIGINT NOT NULL REFERENCES member(id) ON DELETE CASCADE,
  target_member_id          BIGINT NOT NULL REFERENCES member(id) ON DELETE CASCADE,

  proposer_reservation_id   BIGINT NOT NULL REFERENCES reservation(id) ON DELETE CASCADE,
  target_reservation_id     BIGINT NOT NULL REFERENCES reservation(id) ON DELETE CASCADE,

  proposer_slot_id          BIGINT NOT NULL REFERENCES slot(id) ON DELETE CASCADE,
  target_slot_id            BIGINT NOT NULL REFERENCES slot(id) ON DELETE CASCADE,
  -- 제안 시점 스냅샷(수락 후 예약의 slot_id가 바뀌어도 이력 유지)

  status                    swapproposalstatus NOT NULL DEFAULT 'PENDING',
  fail_reason               VARCHAR(64) NULL,
  -- 예: ALREADY_TRANSFERRED | CANCELLED | SLOT_STARTED | NOT_CONFIRMED | CONFLICT

  requested_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
  resolved_at               TIMESTAMPTZ NULL
);

-- 예약당 PENDING 최대 1 (제안자로 걸린 경우)
CREATE UNIQUE INDEX uq_swap_pending_proposer_res
  ON swap_proposal (proposer_reservation_id)
  WHERE status = 'PENDING';

-- 예약당 PENDING 최대 1 (피제안자로 걸린 경우)
CREATE UNIQUE INDEX uq_swap_pending_target_res
  ON swap_proposal (target_reservation_id)
  WHERE status = 'PENDING';

CREATE INDEX ix_swap_target_status ON swap_proposal (target_member_id, status);
CREATE INDEX ix_swap_proposer_status ON swap_proposal (proposer_member_id, status);
CREATE INDEX ix_swap_cycle_status ON swap_proposal (cycle_id, status);
```

### 4.3 모델 스케치 (SQLAlchemy)

```python
class SwapProposal(Base):
    __tablename__ = "swap_proposal"
    id: Mapped[int]
    cycle_id: Mapped[int]
    proposer_member_id: Mapped[int]
    target_member_id: Mapped[int]
    proposer_reservation_id: Mapped[int]
    target_reservation_id: Mapped[int]
    proposer_slot_id: Mapped[int]
    target_slot_id: Mapped[int]
    status: Mapped[SwapProposalStatus]
    fail_reason: Mapped[Optional[str]]
    requested_at: Mapped[datetime]
    resolved_at: Mapped[Optional[datetime]]
```

관리자 FK 없음 (`resolved_by_admin_id` 불필요).

## 5. API

모두 로그인 회원(`get_current_active_member`). 응답 envelope: `{ "data": ... }` (기존과 동일).

### 5.1 후보 검색

`GET /reservation/{reservationId}/swap/targets?q=`

**검색어(`q`)가 비어 있으면 `members: []`를 반환** (전체 확정 목록 덤프 금지). FO는 입력 후에만 호출.

**조건 (목록):**

- `q` 비어 있지 않음 (이름/이메일/부서 `ilike`)
- 같은 `cycle_id`
- `status = CONFIRMED`
- 본인 제외
- 대상 슬롯 시작 전 + 제안자 슬롯 시작 전 + 수 17:00 이후
- 대상 예약에 PENDING swap 없음 / PENDING transfer 없음
- Teams 수신 가능: `entra_oid` 있음 · mock OID·시스템 계정 제외 (양도 `search_transfer_recipients`와 동일 필터 권장)

### 5.2 제안 생성

`POST /reservation/{reservationId}/swap`

```json
{ "targetReservationId": 501 }
```

**Response 201/200:**

```json
{
  "data": {
    "swapId": 9,
    "status": "PENDING",
    "message": "교환 제안을 보냈습니다."
  }
}
```

**서버 처리 요약:**

1. 제안자 예약 FOR UPDATE + 창·CONFIRMED 검증  
2. 대상 예약 FOR UPDATE + 같은 cycle · CONFIRMED · 이중 슬롯 시작 전  
3. 양측 PENDING swap/transfer 배제  
4. `swap_proposal` INSERT PENDING  
5. `SWAP_PROPOSED` enqueue → deliver

### 5.4 수락

`POST /swap-proposals/{swapId}/accept`

```json
{
```

`POST /swap-proposals/{swapId}/reject`

### 5.6 제안자 취소

`POST /swap-proposals/{swapId}/cancel`  
→ `CANCELLED` + `SWAP_CANCELLED` to target (**확정**)

### 5.7 에러 코드 (추가)

`backend/app/core/errors.py`에 추가:

| code | HTTP | message |
| --- | --- | --- |
| `NOT_SWAP_PERIOD` | 409 | 교환 가능 시간(수요일 17:00 이후 ~ 예약 시작 전)이 아닙니다. |
| `NOT_SWAPPABLE` | 409 | 교환할 수 없는 예약입니다. |
| `TARGET_NOT_SWAPPABLE` | 409 | 교환할 수 없는 상대 예약입니다. |
| `SWAP_ALREADY_PENDING` | 409 | 이미 진행 중인 교환 제안이 있습니다. |
| `TRANSFER_IN_PROGRESS` | 409 | 양도 진행 중이라 교환할 수 없습니다. |

| `SLOT_ALREADY_STARTED` | 409 | 예약 시간이 지나 교환할 수 없습니다. |
| `SWAP_NOT_PENDING` | 409 | 이미 처리된 제안입니다. |
| `SWAP_ACCEPT_FAILED` | 409 | 교환을 완료할 수 없어 제안이 종료되었습니다. |

## 6. 수락(Accept) 트랜잭션

양도 `request_transfer`의 FOR UPDATE 패턴을 확장.

```
BEGIN
  1) SELECT swap_proposal WHERE id=:id AND status='PENDING' FOR UPDATE
  2) SELECT reservation(proposer), reservation(target) FOR UPDATE
     — id 오름차순으로 잠가 데드락 방지
  3) SELECT slot(proposer_slot), slot(target_slot) FOR UPDATE
     — id 오름차순
  4) 재검증:
     - 두 reservation.status == CONFIRMED
     - member_id가 제안 스냅샷과 일치
     - reservation.slot_id가 스냅샷 slot과 일치 (중간에 다른 교환이 없었는지)
     - cycle.close_at <= now
     - now < slot_start(proposer) AND now < slot_start(target)
     - 다른 PENDING transfer 없음
  5) 실패 시:
     - status = FAILED, fail_reason = …, resolved_at = now
     - enqueue SWAP_ACCEPT_FAILED → proposer
     - COMMIT
     - raise SWAP_ACCEPT_FAILED
  6) 성공 시 슬롯 맞교환 (unique 제약 주의):
     a. 임시로 한쪽에 slot_id를 바꾸기 전,
        uq_reservation_slot_confirmed 충돌을 피하려면:
        - 두 reservation을 잠시 비확정으로 내리지 않고,
        - PostgreSQL에서 같은 트랜잭션 내 Deferred unique / 또는
        - slot_id 스왑 순서:
          reservation_A.slot_id = NULL 불가(FK NOT NULL)이므로
        **권장:** 두 Slot의 confirmed_reservation_id를 먼저 교차 갱신한 뒤,
        두 Reservation의 slot_id를 교차 갱신.
        구현 시 unique 위반 나면:
          (i) A.slot_id ← target, B.slot_id ← proposer 를 한 문장/CTE로 하거나
          (ii) DEFERRABLE 제약 검토
     b. slotA.confirmed_reservation_id = proposer_reservation_id
        slotB.confirmed_reservation_id = target_reservation_id
        (교차 후 각각 새 소유 예약)
     c. recompute last_used_date (양 회원)
  7) swap.status = ACCEPTED, resolved_at = now
  8) enqueue SWAP_ACCEPTED × 2
COMMIT
deliver_teams_messages(...)
```

**수락 실패 시에도** 피제안자 API는 409를 받고, 제안자는 Teams로 사유를 받는다 (규칙 5·6).

## 7. 양도와의 동시 진행 배제

| 액션 | 차단 조건 |
| --- | --- |
| 양도 시작 (`POST …/transfer`) | 해당 예약이 swap PENDING(제안/피제안 어느 쪽이든) |
| 교환 제안 | 해당 예약 또는 대상 예약에 transfer PENDING · swap PENDING |
| 교환 수락 | 위 재검증 + 양도 직후 상태 변화 |

구현:

- `transfer.request_transfer` 초반에 `_has_pending_swap_involving(reservation_id)` 추가 → `SWAP_IN_PROGRESS`
- `swap.create`에 `_has_pending_transfer` → `TRANSFER_IN_PROGRESS`
- 목록 메타: `transferable` / `swappable` 계산 시 상호 배제
